Tooling risk: the tool as an attack surface

Release 0.17.0. This project parses hostile firmware for a living, which makes it part of the reader's problem rather than only part of the answer. This register lists every component that consumes input it does not control, the guard found by reading that component, and the gap that remains.

Read the none observed rows as written. They mean no bound was found in the module, not that the module is safe. This page is a risk register, not a certification, and nothing on it grades above CORROBORATED.

Where the register stands

  • No component has been fuzzed. There is no harness in tools/ and no corpus in the tree. (CONFIRMED)
  • Python removes the memory-safety class (buffer overflows, use-after-free) that a C parser of the same inputs would carry. It does not remove unbounded allocation, quadratic scanning, or logic errors in length handling. (CORROBORATED)
  • Handling hostile input without executing it is the design and is visible in the code; that it is robust against a determined adversary is not established, and no claim here says so. (CONFIRMED)

Components that parse input they do not control

Module Consumes Guard found Remaining gap
qvault/fingerprints.py firmware bytes and indicator text text-derived grade capped at INFERRED (MAX_TEXT_GRADE) Matching is linear per indicator; an indicator set large enough to be quadratic on a hostile image is not bounded or measured.
qvault/fwdiff.py two firmware images, arbitrary bytes explicit caps: MAX_FILES 4096, MAX_SECTIONS 96, MAX_PE_CANDIDATES 4 Caps bound the count of structures, not the cost of comparing two near-identical large images inside those caps.
qvault/ingest.py evidence blobs from an operator or an acquisition none observed: hashing and metadata capture; bounds come from the caller No independent size ceiling here, so a caller that streams an unbounded blob is trusted not to. That is an assumption, not a check.
qvault/store.py on-disk store files, writable by anyone who reaches the volume O_NOFOLLOW + S_ISREG + O_NONBLOCK on every read, so a symlink, FIFO or device in the namespace is refused rather than followed or hung on; an object made group/world-writable after seal is refused; ids cannot traverse; the seal fsyncs the directory so a crash cannot lose the link while keeping the bytes The reader refuses a link and a widened mode, not a regular 0400 file an attacker wrote as a substitute. Content integrity is the envelope hash plus the audit chain; this open path does not establish it.
qvault/audit.py audit log entries, attacker-writable between runs hash chain with prev_hash and seq continuity; signed Ed25519 checkpoint catches head truncation; a persisted high-water mark refuses to append to a log shorter than the last recorded count, which closes truncate-then-keep-appending Both controls sit on the same volume. Rewriting the mark and the log together, or holding the signing key, defeats them; closing that needs an off-box anchor (RFC 3161, a transparency log, paper custody), which is deployment and not code.
qvault/authorization.py authorization bundles: intent, approvals, policy and receipt as JSON, from whoever presents them every element is verified before it is believed: Ed25519 signatures over domain-separated canonical bytes, the approver fingerprint recomputed from the key rather than read from the file, the policy checked against a supplied root key, the receipt checked against a hash the verifier computed itself, and a bundle version check that refuses anything unexpected Parsing itself is unbounded: a large members map or a huge approvals list is processed before any signature is examined, so a hostile bundle can spend CPU and memory. No fuzzing has been done on the JSON surface. A malformed bundle is reported as MALFORMED rather than raised, which is a behaviour claim, not a hardening claim.
qvault/provenance.py manifests and vendored-source trees hmac.compare_digest for secret-derived comparisons A modified vendored tree is caught only if its pinned hash is checked, and the pin is data in the same repository it is meant to protect.
qvault/retrieve.py object identifiers from a caller hmac.compare_digest on identifier comparison Comparison is constant-time; the surrounding lookup is not, so the guarantee is about one comparison, not about the operation.
qvault/keys.py key material and identifiers none observed at this layer beyond storage; comparisons are delegated Key lifetime and zeroisation are not enforced by the language. Python strings are immutable, so a key in memory is presumed present until the process exits.
qvault/crypto.py sealed ciphertext, which an attacker may control AES-256-GCM: authentication is checked before plaintext is used No adversarial test of chunk framing or truncation; the framing assumptions are covered by unit tests written from the same model as the implementation.
qvault/triage.py bytes from the vendored zbtriage engine vendored at a pinned revision; high-frequency indicator counting fixed after an undercount defect Third-party code is trusted at its pin. Its upstream changes are audited by hand, and that audit is not automated.
qvault/cdup.py sealed ciphertext, wrapped keys and capability tokens, from a caller or an attacker AEAD per chunk with AAD bound to the object id, so ciphertext cannot be relabelled; capability MAC checked with hmac.compare_digest before any key is unwrapped; a single-use replay set; refusals byte-identical across expiry, forgery, replay and wrong-object The authority trusts its own directory for the KEK and the replay set. An attacker who can write that directory reads the key and rewrites spent capabilities; the separation is deployment (another host, an HSM), not this module.
qvault/atrest.py sealed envelopes read back from disk, and the key files under the key root AES-256-GCM with the record id bound in the associated data; wrapped DEKs authenticated before use; hash-linked chain over content identity; append-only; a write that cannot seal leaves nothing behind TPM backing is unverified in an environment with no TPM, and is graded HYPOTHESIS even when a device is present because no attestation is captured. The software protector is defeated by anything that can read its key root, and plaintext exists in memory during seal and after open.
qvault/threatintel.py graded observations supplied by an analyst, plus entity strings collection sources refused on intake and no network code in the module, so it cannot become a collector; per-claim ceilings cap attribution at HYPOTHESIS; grades computed from provenance roots so derived rows cannot launder independence It trusts the grades it is handed. An observation typed CONFIRMED by mistake is believed, and the ceilings limit what that buys rather than catching the error.
qvault/evidence_brief.py a case file (JSON) and the bytes of every artefact it references hashes recomputed from bytes rather than trusted; timezone-mandatory and non-future timestamps; mode-bit immutability; manifest hash that verify recomputes; no identity field exists in the structure The case file is read with json.load and validated field by field, not against a schema, and a hostile case file can still exhaust memory. The lint for person-naming phrasing is four regexes and cannot catch implication by layout.
qvault/inputcapture.py telemetry signals (technique, plane, source) from endpoint tooling corroboration requires two distinct planes; all four innocent explanations must be excluded on the record; CONFIRMED and "clean" unreachable; case grade is the weakest technique Level 4 is unobservable from the host and is reported as such rather than detected. The module cannot tell a hook from a hook's absence, so silence stays UNKNOWN.
qvault/wild.py the in-the-wild dataset (pinned snapshot) pinned snapshot; entries are metadata, not samples Parsed as trusted because it is vendored. If the snapshot is regenerated, nothing re-validates its schema.
qvault/netobs.py LAN telemetry: device records, flow metadata, discovery output BSSID treated as context, never as a key or identity Records are supplied by an agent on a network the adversary may control, so identity claims are corroborated at best.

18 registered components. A test fails if a module takes bytes or parses JSON and is missing from this table, so the register stays complete as the code grows.

What a reader should do with it

Run this on a machine you can rebuild. Treat the evidence store as data written by an adversary, because a bootkit that knows it is being collected will try to write it. Neither of those is a paranoid reading of the code; both follow from the rows above.

What this page does not claim

It does not claim the parsers are safe, bounded, or audited by anyone other than this project. It claims that each component consuming untrusted input is named, that its guard is described at the level it was verified, and that its gap is written down rather than left for a reader to discover during an incident.
