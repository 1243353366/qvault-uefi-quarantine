Telemetry map: what feeds each detection

Generated by tools/gen_telemetry_map.py from qvault/telemetry.py. test_telemetry.py fails if this file and the mapping disagree.

A detection without a named evidence source is an opinion. Each mechanism below lists the telemetry that would carry its evidence, the fields to look at, and any published Sigma family covering the same behaviour. Where a host cannot testify, the row says so and names the source that sits outside it.

Sysmon event semantics are from the Microsoft Sysinternals documentation; Sigma rule identifiers were read from the SigmaHQ repository; ATT&CK v20 vocabulary is Detection Strategy, Analytics and Data Components.

Sigma families cited

  • Suspicious PowerShell In Registry Run Keys (8d85cf08-bf97-4260-ba49-986a2a65129c, logsource registry_set) for run_key: matches a script host in a Run key, the shape QVault reports as lolbin_proxy plus user_writable_location
  • Add Debugger Entry To AeDebug For Persistence (092af964-4233-4373-b4ba-d86ea2890288, logsource registry_set) for run_key: Debugger-value persistence outside IFEO, which is why the mechanism family is wider than one key

Blind spots

  • bootkit_boot: the boot chain runs before any agent; the evidence is the measured boot log and an out-of-band flash read
  • rootkit_hiding: a rootkit conceals its own artefacts from the telemetry agent; only a cross-view differential from outside the host can see it
  • fileless: no autostart artefact exists, so the trace is process ancestry and script blocks at run time; a post-hoc snapshot cannot see it

No row above is a claim of detection coverage. A mechanism with telemetry and no deployment is a mechanism nobody is watching.
